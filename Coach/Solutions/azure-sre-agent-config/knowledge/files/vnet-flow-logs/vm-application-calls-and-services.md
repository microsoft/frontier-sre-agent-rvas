# VM Application Calls And Exposed Services

This guide documents all available application calls between lab VMs, exposed services, ports, who can call what, how to generate traffic manually or via scripts, and how to read scripts line by line.

Document type: operational reference with how-to sections. The intended reader is a cloud/network architect or operator who needs to explain, execute, or debug the VNet Flow Logs + Traffic Analytics demo.

## Scope

This guide includes only what is actually defined in the repository:

- VMs, IPs, subnets, load balancers, and cloud-init mappings from [../terraform/compute.tf](../terraform/compute.tf), [../terraform/locals.tf](../terraform/locals.tf), and [../terraform/outputs.tf](../terraform/outputs.tf).
- NSGs, peering, Azure Firewall, route tables, and UDRs from [../terraform/network.tf](../terraform/network.tf).
- Services installed and listeners exposed by the templates in [../terraform/templates](../terraform/templates).
- Calls generated by the scripts in [../scripts](../scripts).
- Operational queries already documented in [kql-catalog.md](kql-catalog.md).

This guide does not transform the mock services into real services and does not modify Terraform or scripts. The listeners on 8080 and 5432 are intentionally simple: they exist to generate observable flows, not to simulate a production-grade application.

## Exposed Services Catalog

| VM/Object | Port | Service | How it is exposed | Who calls it in the demo |
| --- | --- | --- | --- | --- |
| web-1 | TCP 80 | Static NGINX | `systemctl enable nginx` and `systemctl restart nginx` from cloud-init | direct client and ILB |

| web-1, web-2, api, db | TCP 8080 | API mock | `nohup sh -c 'while true; do echo ... demo-api | nc -l -p 8080 -q 1; done'` | client to api in baseline |

## Call Matrix And Network Controls

| From | To | Port | Expected permission | Controls involved | Notes |
| --- | --- | --- | --- | --- | --- |
| client | web-1/web-2 | 80 | Allowed | app NSG `AllowVnetInbound` and `AllowHttpFromVnet` | intra-spoke app traffic |
| client | ILB web | 80 | Allowed | app NSG + Standard Load Balancer | destination visible as `10.20.2.100` |
| client | api | 8080 | Allowed | data NSG `AllowAppToDataPorts`, firewall network rule wildcard `allow-all` if centralized routing is active | app spoke -> data spoke traffic |
| client | db | 5432 | Allowed in baseline | data NSG `AllowAppToDataPorts`, firewall network rule wildcard `allow-all` if centralized routing is active | becomes denied in the NSG scenario |
| client/data | Microsoft public endpoints | 443 | Allowed if firewall enabled | route `0.0.0.0/0` toward firewall + firewall network rule wildcard `allow-all`; application rule `allow-microsoft-https` remains as a demo reference | generates egress evidence |
| Internet | app/data/hub | any | Denied | NSG `DenyInternetInbound` | the lab does not expose public ingress |
| data -> client return path | return flow | ephemeral | Allowed in baseline | data route table toward firewall | becomes blackhole in the UDR scenario |

When `enable_centralized_firewall_routing = true`, spoke route tables point to Azure Firewall:

- app spoke toward `10.30.0.0/16` via firewall;
- data spoke toward `10.20.0.0/16` via firewall;
- app and data spokes toward `0.0.0.0/0` via firewall.

The Linux NVA is not the default next hop in the demo. It is used to explain the virtual appliance concept and for potential lab extensions, but the operational path is Azure Firewall.

Security note: the lab firewall policy is intentionally permissive (`source=*`, `destination=*`, `port=*`, `protocol=Any`). It makes the firewall an observable centralized transit point; it is not a recommended enterprise baseline configuration.

## Manual Execution Of Calls

The following examples must be run inside the client VM. The most consistent way with the lab is to use Azure Run Command following the same pattern as [Student/Resources/scenarios/scripts/common.sh](Student/Resources/scenarios/scripts/common.sh).

Direct example with Azure CLI:

```bash
az vm run-command invoke \
  --resource-group "$(terraform -chdir=terraform output -raw resource_group_name)" \
  --name "$(terraform -chdir=terraform output -json demo_scenario_resource_names | jq -r .client_vm)" \
  --command-id RunShellScript \
  --scripts "curl -m 3 -s http://10.20.2.10/" \
  --query "value[0].message" \
  --output tsv
```

Explanation of the main tokens:

| Token | Meaning |
| --- | --- |
| `az vm run-command invoke` | Executes a script inside an Azure VM without opening SSH. |
| `--resource-group` | Specifies the resource group that contains the VM. |
| `terraform -chdir=terraform output -raw resource_group_name` | Reads the resource group name from the Terraform state. |
| `--name` | Name of the target VM. Here it is read from the `demo_scenario_resource_names.client_vm` output. |
| `--command-id RunShellScript` | Tells Azure to execute a Linux shell script. |
| `--scripts` | Body of the remote command. |
| `curl -m 3 -s` | Performs HTTP with a 3-second timeout and silent output. |
| `--query "value[0].message"` | Extracts only the message produced by the remote command. |
| `--output tsv` | Prints tab-separated text, more readable in scripts. |

Useful manual commands inside the client:

```bash
curl -m 3 -s http://10.20.2.10/
curl -m 3 -s http://10.20.2.11/
curl -m 3 -s http://10.20.2.100/
curl -m 3 -s http://10.30.1.10:8080/
timeout 2 bash -c '</dev/tcp/10.30.2.10/5432'
curl -m 3 -s https://www.microsoft.com/
```

Important tokens:

| Token | Explanation |
| --- | --- |
| `curl` | HTTP/HTTPS client used to generate application traffic. |
| `-m 3` | Maximum timeout of 3 seconds; prevents long blocks during the demo. |
| `-s` | Silent mode; reduces output noise. |
| `http://10.20.2.10/` | HTTP URL to web-1 port 80. |
| `http://10.30.1.10:8080/` | HTTP URL to the API mock port 8080. |
| `timeout 2` | Terminates the command if it does not finish within 2 seconds. |
| `bash -c` | Executes the following string as a Bash command. |
| `</dev/tcp/10.30.2.10/5432` | Bash feature that opens a TCP connection to the given IP/port. Does not send any application payload. |

## Baseline Workflow

1. Validate that the lab is deployed and that Flow Logs/Traffic Analytics are configured:

   ```bash
   Student/Resources/scenarios/scripts/validate-demo.sh
   ```

2. Restore any faults left by previous demo runs:

   ```bash
   Student/Resources/scenarios/scripts/restore-nsg-block.sh
   Student/Resources/scenarios/scripts/restore-udr-asymmetry.sh
   ```

3. Generate baseline traffic:

   ```bash
   Student/Resources/scenarios/scripts/generate-baseline-traffic.sh
   ```

4. Wait at least the configured Traffic Analytics cycle. The lab typically uses 10 minutes; in standard configurations it may be 60 minutes. Log Analytics ingestion may add additional latency.

5. Run operational queries:

   ```bash
   Student/Resources/scenarios/scripts/run-kql.sh top-talkers
   Student/Resources/scenarios/scripts/run-kql.sh flow-types
   ```

Expected evidence: allowed flows from client to web, ILB, API, DB, and Microsoft public endpoints. The full demo explanation is in [demo-runbook.md](demo-runbook.md).

## NSG Block Scenario Workflow

This scenario simulates a block toward the database.

```bash
Student/Resources/scenarios/scripts/trigger-nsg-block.sh
```

Effect:

- creates the NSG rule `Demo-Deny-App-To-Db-5432` on the data NSG;
- priority `102`, therefore higher priority than the baseline allow rule `200`;
- direction `Inbound`;
- action `Deny`;
- source `10.20.0.0/16`;
- destination `10.30.2.10`;
- destination port `5432`;
- generates 25 TCP probes from client to DB.

Query:

```bash
Student/Resources/scenarios/scripts/run-kql.sh denied
```

Expected evidence:

- `FlowStatus == "Denied"` (full word, not `D`);
- `AclRule` contains `Demo-Deny-App-To-Db-5432`;
- `SrcIp` close to `10.20.1.10`;
- `DestIp == 10.30.2.10`;
- `DestPort == 5432`.

Restore:

```bash
Student/Resources/scenarios/scripts/restore-nsg-block.sh
```

Root cause and extended narrative are in [troubleshooting-scenarios.md](troubleshooting-scenarios.md).

## UDR Asymmetry Scenario Workflow

This scenario simulates an incorrect more-specific route that breaks the return path from the data spoke to the client.

```bash
Student/Resources/scenarios/scripts/trigger-udr-asymmetry.sh
```

Effect:

- creates or updates the route `Demo-Break-Return-To-App-Client` in the data route table;
- address prefix `10.20.1.0/24`;
- next hop type `None`;
- generates 20 TCP probes from client to DB.

Why this works as a fault: Azure applies longest prefix match. The route `10.20.1.0/24 -> None` is more specific than the baseline route `10.20.0.0/16 -> firewall`, so the return traffic toward the client is dropped by the data subnet.

Expected evidence:

- Next Hop client -> DB still shows `VirtualAppliance` toward Azure Firewall;
- Effective routes on the data spoke show `10.20.1.0/24 -> None`;
- Traffic Analytics may show unbalanced byte counts or missing expected return traffic.

Restore:

```bash
Student/Resources/scenarios/scripts/restore-udr-asymmetry.sh
```

## Cloud-Init Breakdown

### Client Cloud-Init

Source: [../terraform/templates/client-cloud-init.yaml](../terraform/templates/client-cloud-init.yaml)

```yaml

package_update: true
packages:
  - curl
  - netcat-openbsd
  - iperf3

```

| Line/token | Explanation |
| --- | --- |
| `#cloud-config` | Header that tells cloud-init to interpret the file as a cloud-init configuration. |
| `package_update: true` | Updates the package index before installation. |
| `packages:` | List of packages to install in the VM. |
| `curl` | HTTP/HTTPS client used to generate requests to web, API, and public endpoints. |
| `netcat-openbsd` | Package that provides `nc`; useful for TCP tests and mock listeners. |
| `iperf3` | Performance testing tool. Installed for lab extensions, not used in the current baseline. |
| `runcmd:` | Commands executed at the end of cloud-init configuration. |
| `echo "client ready"` | Writes a textual readiness marker. |
| `>` | Redirects stdout to the specified file, overwriting it. |
| `/var/log/vflta-client-ready.log` | Local file that signals that the basic client configuration has completed. It is not an application health probe. |

### Web/API/DB Cloud-Init

Source: [../terraform/templates/web-cloud-init.yaml](../terraform/templates/web-cloud-init.yaml)

This template is used by web-1, web-2, api, and db. For this reason the mock listeners 8080 and 5432 are present on all these VMs.

| Line/token | Explanation |
| --- | --- |
| `nginx` | Installs the web server that listens on TCP 80. |
| `write_files:` | Creates files during provisioning. |
| `path: /var/www/html/index.html` | Static file served by NGINX. |
| `permissions: '0644'` | Owner writes; group and others read. |
| `vnet-flow-logs-demo` | Body of the web page used to verify the HTTP response. |
| `systemctl enable nginx` | Enables NGINX at VM startup. |
| `systemctl restart nginx` | Starts or restarts NGINX immediately. |
| `nohup` | Keeps the process alive even after the cloud-init session ends. |
| `sh -c '...'` | Executes the quoted string as a shell script. |
| `while true; do ... done` | Infinite loop: the listener is recreated after each connection. |
| `echo "HTTP/1.1 200 OK\r\n\r\ndemo-db"` | Generates a minimal HTTP response with payload `demo-db`. `\r\n\r\n` separates header and body. |
| `|` | Pipe: passes the output of `echo` to `nc`. |
| `nc -l -p 5432 -q 1` | Netcat listens (`-l`) on port (`-p`) 5432 and closes after 1 second (`-q 1`). |
| `>/var/log/demo-db-listener.log` | Writes the process stdout to the DB mock log. |
| `2>&1` | Redirects stderr to stdout, therefore to the same log file. |
| `&` | Sends the process to the background. |
| `demo-api` / `8080` | Equivalent variant for the API mock listener. |

Intentional limitations:

- This is not a complete REST service.
- This is not PostgreSQL, even though it uses port 5432.
- Each `nc` handles one connection at a time; sufficient for a demo, not for concurrent load.

## Troubleshooting Notes

- If queries return empty results, first check raw blobs in the Storage Account and wait for the Traffic Analytics cycle to complete.
- If `trigger-udr-asymmetry.sh` fails with a null firewall, centralized routing is not enabled in Terraform outputs.
- If DB traffic does not appear as denied after the NSG scenario, verify that the rule `Demo-Deny-App-To-Db-5432` exists in the data NSG and that ingestion has completed.
- If counts appear duplicated, remember that flows may be observed from multiple capture points. Use `FlowDirection` and the anti-duplication queries in [kql-catalog.md](kql-catalog.md).
- If mock listeners do not respond immediately after deployment, cloud-init may not have completed the background processes. Check the logs in the VM or wait a few minutes.
