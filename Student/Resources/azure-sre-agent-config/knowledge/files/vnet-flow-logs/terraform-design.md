# Terraform Design

## Provider

- `hashicorp/azurerm`: main Azure resources and `azurerm_network_watcher_flow_log`.

The detailed guide for activation, parameters, and Terraform decisions is [vnet-flow-logs-traffic-analytics-terraform-guide.md](vnet-flow-logs-traffic-analytics-terraform-guide.md).

Sources:

- https://registry.terraform.io/providers/hashicorp/azurerm/latest/docs/resources/network_watcher_flow_log
- https://learn.microsoft.com/en-us/azure/templates/microsoft.network/networkwatchers/flowlogs

## Main Files

- `versions.tf`: provider versions.
- `providers.tf`: AzureRM configuration.
- `network.tf`: VNet, subnets, peering, NSG, Azure Firewall, firewall policy, route table and UDR associations.
- `compute.tf`: demo VMs, local password auth, Boot Diagnostics, NVA, internal load balancer.
- `monitoring.tf`: Storage, Log Analytics, VNet Flow Logs, Workbook, Alert.
- `private-endpoint.tf`: optional Private Endpoint scenario.
- `outputs.tf`: names and IPs used by scripts.

## Applied Best Practices

- Dedicated Storage for flow logs.
- Short retention for demos.
- No public IPs on VMs.
- Administrative access via Azure Bastion in the hub VNet.
- Linux VMs with local admin password for demo simplicity; no SSH keys generated by Terraform.
- Boot Diagnostics enabled on all VMs.
- Centralized routing by default via Azure Firewall Basic in the hub.
- App/data route tables managed by Terraform and associated with workload subnets.
- Traffic Analytics at 10-minute intervals to reduce wait times during demos.
- Alerts disabled by default via `enable_alerts = false` in the tfvars example.

## Centralized Routing

The lab default is `enable_centralized_firewall_routing = true` with `azure_firewall_sku_tier = "Basic"`.

Terraform creates:

- Subnet `AzureFirewallSubnet` in the hub.
- Subnet `AzureFirewallManagementSubnet` in the hub, required by the Basic SKU.
- Standard Public IP for Azure Firewall.
- Azure Firewall policy with wildcard network rule `allow-all` to permit all flows routed through the firewall.
- UDR app -> data, data -> app and `0.0.0.0/0` toward the firewall's private IP.
- Route table associations on `snet-client`, `snet-web`, `snet-api` and `snet-db`.

Azure Firewall Basic is sufficient for the demo because it supports stateful filtering, outbound SNAT, network rules, and application FQDN filtering. The lab policy uses a permissive wildcard network rule (`source=*`, `destination=*`, `port=*`, `protocol=Any`): this is a demonstration choice, not an enterprise security baseline. Source: https://learn.microsoft.com/en-us/azure/firewall/features-by-sku#azure-firewall-basic-features

## VM Access, Bastion, and Boot Diagnostics

The lab uses `admin_password` and `disable_password_authentication = false` on `azurerm_linux_virtual_machine`, removing `admin_ssh_key` and `tls_private_key`. This satisfies the password-only requirement and prevents Terraform from generating demo private keys in the state. Terraform source: https://registry.terraform.io/providers/hashicorp/azurerm/latest/docs/resources/linux_virtual_machine

Trade-off: Microsoft recommends SSH keys over passwords for Linux; the local password is accepted here for demo simplicity because VMs have no public IP and access goes through Bastion. Source: https://learn.microsoft.com/en-us/azure/virtual-machines/linux/create-ssh-keys-detailed

Azure Bastion is deployed in the hub VNet with a dedicated `AzureBastionSubnet` (`10.10.5.0/26`) and a static Standard public IP. The default SKU is `Basic`, sufficient for browser access from the portal; `Standard` enables native client, tunneling, file copy, IP-based connection, and custom ports. Sources: https://learn.microsoft.com/en-us/azure/bastion/configuration-settings, https://learn.microsoft.com/en-us/azure/bastion/bastion-connect-vm-ssh-linux

Boot Diagnostics is enabled with the `boot_diagnostics {}` block without a custom storage account, so Azure uses managed storage. Source: https://learn.microsoft.com/en-us/azure/virtual-machines/boot-diagnostics

## Controlled Faults and Restore

Permanent routes and rules remain Terraform-managed. Demo scripts should only create temporary overlays:

- `trigger-nsg-block.sh` adds an NSG deny rule to simulate an application block.
- `restore-nsg-block.sh` removes the temporary rule.
- `trigger-udr-asymmetry.sh` adds a more specific route `10.20.1.0/24 -> None` on the data spoke.
- `restore-udr-asymmetry.sh` removes the temporary route.

This prevents the demo from turning a troubleshooting scenario into permanent drift. After restores, `terraform plan -detailed-exitcode` should return with no expected changes.

## Private Endpoint

The Private Endpoint scenario is optional and governed by `enable_private_endpoint_demo`. The Private Link subnet is not associated with the fault demo route tables: flow visibility should be read from the source VM side, not on the Private Endpoint itself.

Source: https://learn.microsoft.com/en-us/azure/network-watcher/vnet-flow-logs-overview#private-endpoint-traffic
